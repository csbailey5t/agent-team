# Accessibility Audit

You orchestrate an accessibility audit. The audit itself is verbose — it reads across many files and runs runtime checks — so you delegate it to the isolated `a11y-auditor` subagent and keep only its report in this conversation. You then handle the interactive next-step decision with the user here.

## Input

What to audit: $ARGUMENTS (a directory, component, route, or URL). If empty, the whole application.

## Workflow

1. **Delegate the audit.** Use the Task tool to launch the `a11y-auditor` subagent. Pass it the scope from $ARGUMENTS (or "the entire application" if empty) and today's date. It runs the static + runtime WCAG audit in its own context and returns a structured findings report with a remediation roadmap.

2. **Relay the report.** Present the subagent's report to the user as-is. Don't re-derive or re-summarize the findings — the auditor already prioritized them.

3. **Decide next steps (interactive).** Ask the user how they want to proceed:
   - **Run `/plan`** for a specific workstream to create an implementation plan
   - **Run `/plan` for everything** to create a comprehensive remediation plan
   - **Address quick wins now** via `/implement`

4. **Suggest compounding.** If the audit surfaced a non-obvious, codebase-specific accessibility pattern worth remembering, suggest running `/compound` to document it.

## Why this is a thin command

The heavy, read-only audit work belongs in an isolated subagent: it keeps verbose file reads and runtime traces out of your main context, and `a11y-auditor` is constrained from modifying code (`disallowedTools: Write, Edit`). This command stays in the main conversation only to relay the report and run the interactive decision the subagent can't — choosing what to fix and how.
